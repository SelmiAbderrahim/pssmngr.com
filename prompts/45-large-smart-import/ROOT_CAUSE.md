## 3. Reproduced boundaries on this checkout

### 3.1 Every parsed row is mounted as a preview row

`ImportWizard.tsx:230` renders `parseResult.items.map(...)` with no slice or
pagination, inside a `max-h-[400px]` scroll container. A 300-record file mounts
300 `ImportPreviewRow` components, each with a `Checkbox`, at once. There is no
pagination state to clamp after parse, delete, back, retry, or close.

### 3.2 Selection is O(n²) on every render

`ImportWizard.tsx:235` computes `selectedItems.includes(item)` per row against
the selected array. For 300 items that is up to 90,000 reference comparisons per
render pass, and it compares object identity rather than an exact-duplicate
fingerprint, so no duplicate detection reaches the row level at all.

### 3.3 No input bounds before reading

`useImportPipeline.uploadFile` calls `readFile(file)` immediately
(`pipeline.ts:38`) with no `File.size` pre-check, no character ceiling, and no
item ceiling. An arbitrarily large file is read fully into memory and parsed.
There is also no paste path — `ImportWizard.tsx:104` accepts only `.csv,.json`
through a file input, so the pasted / `.txt` / labelled `key: value` input the
goal requires cannot be entered.

### 3.4 Stale results are not cancelled

`uploadFile` is a plain async callback with no run token. Selecting a second
file while the first is still reading, or closing the dialog mid-read, still
applies the older parse to state, leaving plaintext preview state mounted after
reset.

### 3.5 Retry is not idempotent — this is the real duplicate-write defect

`pipeline.ts:167` calls `credentials.batchCreate` with `{ vaultId, items }` and
no idempotency key, and `credentials.batchCreate` neither accepts
`idempotencyKeyZodSchema` nor runs through `runWithIdempotency`
(`credentials.ts:181-224`), even though `create`, `update`, and `softDelete` in
the same router all do (`credentials.ts:138`, `:307`, `:367`). A batch that
times out after the server committed its insert, and is then retried, inserts
the same 50 items a second time. For a 300-record import that is up to 300
duplicated vault items from one retry.

### 3.6 Shared vaults have no batch path at all

`shared-vault.ts` exposes `addItem` (single item, `:1091`) and no batch
procedure. Importing 300 items into a shared vault is therefore 300 sequential
round trips. `useVaultItems.handleCreateItem` (`useVaultItems.ts:492`) refreshes
the vault with `await fetchItems(...)` after **every** single write
(`:505`, `:551`), so any caller looping it pays 300 writes plus 300 full vault
refetch-and-decrypt cycles. There is no bulk method on the hook, so the wizard
and the vault page cannot share one encrypted batch path.

### 3.7 Zero-knowledge status

No plaintext leaves the browser today: `pipeline.ts:140` encrypts with
`vaultCrypto.encryptItem` before any mutation, and `credentials.batchCreate`
accepts only `encryptedItemFields` under `.strict()`. The documented
zero-knowledge conflict in the prompt does not exist on this checkout. The
requirement that remains is to **keep** it true across the new paste input, the
new shared-vault batch procedure, the new idempotency keys, and the new preview
UI — and to prove it with regression coverage.

## 4. Selected design

Smallest change that meets the goal without adding a dependency, migration,
plaintext column, crypto primitive, provider, worker, queue, or entitlement:

1. **`client/src/services/import/smart-parse.ts`** — one pure entry point.
   Rejects by `File.size` before reading, enforces a 100,000-character ceiling
   and a 500-item defensive ceiling, routes `.pssmngr` bundles to the existing
   encrypted Import/Export flow, reuses `detectParser` for CSV/JSON, and adds
   only a labelled `key: value` block fallback for `.txt` and pasted text. No
   `fetch`, tRPC, AI SDK, logging, or analytics. Returns typed, translatable
   codes and row/block warnings that never embed the source text.
2. **`credentials.batchCreate`** gains the existing optional
   `idempotencyKeyZodSchema` field and runs through `runWithIdempotency`;
   **`sharedVault.batchAddItems`** is added with the same encrypted-item
   schema, one `requireVaultPermission(..., "edit", ...)` check, one atomic
   multi-row insert scoped to `sharedVaultId` and `createdBy`, and
   `{ created: number }` through `runWithIdempotency`.
3. **`useVaultItems.bulkCreateItems`** — sequential groups of at most 50,
   parallel encryption within a group through the existing `encryptItem` /
   `encryptItemWithKey` calls, per-user vs shared routing, idempotency keys
   derived only from `(operationId, vaultId, batchIndex)`, saved/failed original
   keys returned, and exactly one `fetchItems` refresh after the run.
4. **`ImportWizard`** — paste input, 50 rows per page with clamping,
   accessible pagination, live announcements, logical RTL properties, a shared
   exact-duplicate fingerprint used through `Set` for O(n) checks, and retry
   that reuses the operation id so only failed batches are re-sent.
